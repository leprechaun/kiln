# 06: StaticWebsite — full pipeline, including nested-XR generator support

**What to build:** `StaticWebsiteSpec` (referencing `DnsValidatedCertificateSpec` for its nested cert instance), `composeStaticWebsite` (which emits a nested `DnsValidatedCertificate` instance among its resources), and the generator extended to handle a compose function emitting another kind's own schema instance. This is where the previously-deferred nested-XR requirement actually gets resolved.

**Blocked by:** 01, 03, 05 (needs `DnsValidatedCertificateSpec` to exist to type-check the nested instance it constructs)

**Status:** done

- [x] `StaticWebsiteSpec` is designed from the consumer's perspective (bucket name, custom domain, region, an existing Route53 zone ID), and includes `[str]: any` so it stays open to the `spec.crossplane` metadata a real XR carries
- [x] `composeStaticWebsite(oxr, ocds) -> [...]` follows the same house rules as ticket 02, and constructs a `DnsValidatedCertificate` instance typed against that kind's own composition schema (`schemas_compositions.DnsValidatedCertificateSpec`) as one of its emitted resources
- [x] `kcl test` passes for `composeStaticWebsite` (6/6), covering cold-start, partially-observed (cert validated, distribution not yet observed), and fully-observed scenarios
- [x] The generator correctly handles a compose function emitting an instance of another kind's own composition schema — see findings: it needed **zero code changes**
- [x] `crossplane composition render` succeeds against the generated StaticWebsite Composition (automated in `tests/integration/test_render_staticwebsite.py`), verified both cold-start and fully-observed via `--observed-resources`

**Findings:**

1. **The deferred "nested-XR generator gap" turned out not to be a gap in this architecture at all.** The original worry (recorded when the spec was written) was that a Phase-5 generator might assume every emitted resource is either the current kind's own spec or a flat provider object. But this generator never inspects what a compose function actually emits — it only (a) concatenates `schemas_providers.k` + `schemas_compositions.k` + the compose function into one source string, and (b) wraps that in the Composition pipeline step. Since `schemas_compositions.k` already holds *every* kind's XR schema (not just the current one), referencing `DnsValidatedCertificateSpec` from inside `composeStaticWebsite` is no different, mechanically, than referencing any other type. Verified by generating StaticWebsite's manifest with the exact same `generate-manifests` invocation used for every other kind, then confirming the nested instance renders correctly — its `apiVersion` (`platform.kcl-first.io/v1alpha1`) is genuinely distinct from the provider-managed resources (`s3.aws.m.upbound.io/v1beta1`, etc.), confirming Crossplane treats it as a real composite resource, not inert data.
2. **The richest resource graph of the four kinds**, deliberately kept to a bounded, realistic scope: `Bucket` + `BucketPolicy` (public-read, both immediate from spec) + nested `DnsValidatedCertificate` (immediate) → gates `Distribution` (CloudFront, needs the nested cert's own `status.certificateArn` — note: not `status.atProvider`, since this reads another XR's status, not a provider resource's) → gates a Route53 alias `Record` and `status.cloudFrontDomainName` (both need `Distribution`'s own `status.atProvider.domainName`). Skipped `OriginAccessControl`/website-hosting-config/a separate `CertificateValidation`-gated wait to keep scope bounded — a public-read bucket via `s3OriginConfig` is simpler and still realistic.
3. **A real, easy-to-miss AWS constraint, respected deliberately:** CloudFront only accepts ACM certificates issued in `us-east-1`, regardless of which region the rest of the site's resources live in — the nested cert's `region` is hardcoded to `"us-east-1"`, not reused from `spec.region` (which governs the bucket).
4. Two more instances of already-known KCL footguns, both caught immediately by `kcl test` and fixed the same way as in tickets 04/05: a type annotation on a dict-literal key (`spec: Type = {...}` inside a literal, not just the dotted-path case from ticket 05) isn't valid — only local variable bindings can carry a type annotation; and leading-`+` line continuation isn't supported.
